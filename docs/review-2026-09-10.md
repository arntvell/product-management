### `48afb47` — Collections: carry-over is now a reviewed bulk action

**Look at:** <http://localhost:3000/catalog/collections?c=FW26>

This is the one you called out: *"the carry into toggle can be often misused and
it's always active."* It was worse than it looked. The season lived in a page-level
selector at the top, every row carried a live `+ Carry over` button, and one click
wrote immediately — into whatever season the selector happened to be set to.

And because `Price` is a separate per-season row that nothing copies, the carried
product silently had **no price for its new season**. It then looked correct in
every list and failed only at push. That is exactly what happened to Barnes Japan
Fade today.

What to check:

- The page-level "Carry into" selector is gone. The season now sits in the action
  bar, next to the button that uses it.
- Tick some rows → an action bar appears → **Carry into FW26…** opens a preview
  saying how many will be added, how many will land **with no FW26 price**, and how
  many of those are priced in another season (so carry-forward can fill them).
- Nothing is written until you confirm.
- **Remove from FW26…** is the undo, same shape.
- Filters you asked for: search (name, style, SKU, vendor), vendor, product type,
  tag, plus a "No price for FW26" filter.
- Sticky header — scroll and the columns stay.
- Full window width instead of `max-w-5xl`.
- An amber banner appears when products in the season have no price for it, with a
  one-click filter to see them. That banner would have shown you Barnes.

The CORE toggle stayed inline: it is idempotent, reversible, and visible, so it
doesn't carry the same hazard.

## 4. Decisions I made for you — reverse any of these

### 4.1 Carrying products forward does NOT copy prices

You said carry-overs are repriced per season per product. So instead of filling the
gap automatically, the UI **shows** it: a "No price" badge per row, a count in the
confirmation, and a filter. The hole is the signal.

*To reverse:* call `runCarryPrices` from the carry-over action. It would need a
colorway filter — it currently takes season, vendor and core only (one line in
`carry-prices.ts`).

### 4.2 Eligibility is derived from `Brand.isLivid`, not stored per product

Loom eligibility is a fact about what a product *is*, not an intent someone ticks.
I keyed it off `Brand.isLivid` and deliberately **not** off `Source`: a Livid
garment is Livid whether it came via Threadflow or Cin7 (87 Loom publications are
Cin7-sourced), and `Source` becomes pure history once Cin7 retires.

Verified safe before relying on it: `isLivid` is set on exactly one brand, and
**no colorway has a null `brandId`** — nothing falls through.

*To reverse:* the rule is three small functions in `readiness.ts`. Change them and
every caller follows.

### 4.3 I did not touch `CatalogGrid`

I planned to make Collections and Publishing reuse it, then dropped that. It is
1,810 lines with editing, paste, copy-down and autosave interwoven; adding a
read-only mode under a clock risks the one surface you said works. Collections got
the same *capabilities* (search, filters, sticky header, full width) in its own
table instead.

*This is the main thing I'd want your call on* — see §5.

## 5. What I would do next, in order

1. **Publishing gets the same treatment as Collections** — search, category/tag/type
   filters, sticky header, full width. It has only season, and all/active/dropped.
   Straightforward now that the pattern exists.
2. **A Shopify fix surface.** The Fix grid is Loom-only. A Shopify blocker has
   nowhere to go, which is why "not ready → go fix it" feels counter-intuitive.
   Readiness should be per-channel and eligibility-aware everywhere.
3. **The product page gains prices, technical/customs and readiness.**
   `/catalog/colorways/[id]` already has the editor, references and channels
   panels. Missing: prices (editable nowhere but the bulk grid's single NOK
   column), customs (reachable only via the Fix grid), and any statement of why a
   product can't be pushed. Media is a separate page that should be a section.
4. **Then decide on `CatalogGrid`.** Either extract its filter/selection machinery
   into a shared hook that every list uses, or accept two implementations. Worth a
   conversation, not a unilateral refactor.

### Still blocked, unchanged

**Wholesale prices have no edit path anywhere in the app.** The bulk grid edits
NOK MSRP only, and Threadflow seasons carry a 7-currency × 2-type matrix. 99
products have no price in any season. This is the real pricing build and it did
not fit in the hour.

**Vintage needs access control first.** One shared `APP_PASSWORD`, no roles, and
every catalog API takes arbitrary ids — so a photographer's login today reaches the
live Shopify metafield editor. The boundary has to be the API layer, not URL
prefixes. Detail in `docs/vintage-drops-integration.md` and the memory note.

**Vintage is weekly.** 40–60 styles every Friday, not an occasional import. That
raises the photo-discovery and validation work from "nice" to critical path.
