# Roadmap — from a correct master to an automated one

Written 2026-09-13, after the barcode fill closed. Ordered by dependency, not by
topic: each phase needs the one above it. Every item says what unblocks it and
what it costs, so the list can be cut from the bottom without breaking anything.

## 0. What changed today, and two things that need a decision before a deploy

### The Shopify fill is already done — the answer is 0, not 87

The recommendation was to fill Origio's blank barcodes from Shopify next. Measured
against the live database rather than yesterday's snapshot, **there is nothing to
fill.** The 175 taken from Sitoo absorbed the whole overlap. Seven blanks matched a
Shopify code and all seven were correctly refused:

| | |
|---|---:|
| Shopify holds the code on two live variants (`EXT-PR-AVR-VLGR-9.5`) | 1 |
| The code already sits on another Origio variant (`LIV-NEEDLE-W-*`) | 6 |

`scripts/fill-barcodes-from-channel.py` is the reusable version of what was an
ad-hoc script for the Sitoo run, with both guards written down.

### The blank-barcode exposure is 53 rows — but only 5 need a barcode

I quoted ~300 from an older count. The real breakdown of the 4,324 blanks:

| | | |
|---|---:|---|
| SS27 / FW26+SS27 pre-season merchandise | 4,057 | Correct. Not made yet. |
| Archived merge tombstones | 107 | Inert. |
| Consumable, material, aggregate, service, sample | 107 | Correct. Not scannable garments. |
| **Live merchandise, no barcode anywhere** | **53** | Looked like the gap. |

Then I applied the qualifier this project keeps forgetting — **stock**. Of the 53,
**48 have no units in Sitoo or Cin7.** They are retire candidates, not gaps, and the
list says so out loud once you read it rather than count it:

- `EXT-PF-PIN125-OS` is named **"Piñon 12.5 Oz Candle - feil sku"** — *wrong SKU*.
  Allocating a barcode would cement a known mistake into identity.
- `LIV-JNE-TRSR-HP-NV-W31-L34` is **SS19**.
- `EXT-RW-*` (10 rows) and `EXT-PR-AVR-VLGR-9.5` are external brands with their own
  manufacturer EANs. Paraboot's is *already in Shopify* — see the next finding.

**Allocation is a one-way door**: `recordIssued` writes the number to the ledger and
it can never be reissued. So the allocator's first real run is **5 rows, not 53**:

| | |
|---|---|
| `LIV-NSH-BLCK-2XL`, `LIV-XWLWTC-JPDWN-42`, `LIV-XWLWTC-JPSH-42` | Livid, 1 unit each — allocate from `7072536` |
| `VN-ONLN-10023-OS`, `VN-ONLN-10025-OS` | Vintage one-of-ones — follow the vintage rule, not the Livid range |

The other 48 go to the retire list for review, not the allocator.

### Shopify has 2 live shared barcodes, not 41

`push-barcodes.ts` carries the number 41 in a comment and it is wrong — that count
included archived variants. Measured on live products only: **2**, and both are two
sizes of one style sharing a code.

```
3606621489698   EXT-PR-AVR-VLGR-7.5   | EXT-PR-AVR-VLGR-9.5
4582746159205   EXT-RTTO-...-RYL-BL-M | EXT-RTTO-...-RYL-BL-S
```

(103 including archived.) Small, but it matters for §3.5 specifically: Loom joins
Shopify orders to Sitoo scans on identity, so each shared code is an ambiguous order
line in the registry. Fix at source or accept it explicitly — not silently.

### `LIV-NEEDLE-W` is a genuine duplicate

Cin7 imported `LIV-Needle-W` (barcoded); Threadflow created `LIV-NEEDLE-W`
(blank). Same garment, two colorways, differing only in case. Checked across the
whole catalogue: **it is the only case-only pair.** One merge, not a class.

### Risk 1 — production runs 55-commit-old code against a migrated database

`main` deploys to Vercel and is 55 commits ahead locally, unpushed. The shared Neon
database has had seven migrations applied, including `Variant.barcode @unique`.

Checked: there is **no `vercel.json`, no cron route, no scheduled writer**, so
nothing is running unattended against the new index. The additive migrations are
harmless to old code. This is not on fire — but it means production has none of
this work, and the gap grows.

### Risk 2 — auth exists, but it fails open and has no roles

I first reported this as "no authentication at all". That was wrong: `middleware.ts`
sits at the repo root, not under `src/`, so my search missed it. It gates every path
except `/login` behind a shared password, and **`APP_PASSWORD` is set in Production**,
so the deployed app is not open.

Three real things remain:

| | |
|---|---|
| **It fails open** | `if (!password) return NextResponse.next()`. If the variable is ever unset, rotated away or missing on a new environment, every write route opens silently. It should hard-fail in production instead. |
| **One shared password, no roles** | Everyone who can read the catalogue can also push to Sitoo, Shopify and Loom. This is the same gap that is step 0 for the vintage module (§5.4). |
| **Bearer token compares to the same secret** | Fine for a script you run; not something to hand out. |

Checked while verifying this: **`SITOO_*` credentials are not set in Production** —
only Shopify, Loom, Threadflow and Cin7. So after the push the Sitoo writer is inert
in production. That is a useful accident today and a to-do before §6 automation.

**Revised call: this does not block the push.** Tighten the fail-open to a hard-fail
first, which is a few lines.

### The Needle merge is applied

Survivor is the Threadflow row `LIV-NEEDLE-W`; it now holds all **6 barcodes**,
both extra seasons (CONTINUITY, FW26, SS27) and all 16 prices. The Cin7 row is
parked as `LIV-Needle-W--merged-into-8a02c8df` and archived, with 0 attachments
left. Catalogue-wide: **0 duplicate barcodes, 10,457 barcoded** — unchanged,
because the codes moved rather than being added.

It was safe for a specific, checked reason: **both rows already pointed at the
same Shopify product** (`gid://shopify/Product/7586896347385`) and the same six
Sitoo products. Retiring the loser therefore withdraws nothing — the survivor
holds the identical publication. That is what justified overriding the
published-loser blocker, and it is the test to apply to any other merge.

### It also uncovered a defect that blocked *every* merge

`Variant.barcode` became unique on 2026-09-11, after `merge-colorways.ts` was
written. The fold copied the loser's barcode onto the survivor while the loser
still held it, so the two rows collided on the index and the merge failed
outright. Fixed the same way `apply-barcodes.ts` handles a rotation — release,
then write, as one transaction. The 12 high-confidence and 58 review-tier pairs
would all have hit this.

### 11 more twins exist, and they are NOT the same safe shape

Same defect class — one garment held twice, once from Threadflow and once from
the Cin7 import, matching on style and colour name with full size overlap:

**Do not batch these.** Unlike Needle, the Threadflow side has **zero channel
links** in every one of the eleven — only the Cin7 row is known to Sitoo and
Shopify. So the survivor rule and the "same channel record" test that made Needle
safe do not apply, and each needs a decision about which SKU the business keeps.
They also will *not* break the sync: the two SKUs differ, so Threadflow never
tries to write the Cin7 barcode onto its own row. This is work for 2.3, not
tonight.

Note the pattern in the SKUs — `LIV-INTL-` against `LIV-M-NTL-`, `LIV-ABY-` against
`LIV-W-BBY-`. Cin7 dropped the gender segment and ran the letters together. That is
the same abbreviation drift as `EEXT-`/`EXT-` and `KRI`/`KR-JPN`.

## 5. The builders

This is the work that stops the cleanup recurring. Three builders, one shared spine.

### 5.1 Shared spine — build once

| | |
|---|---|
| **SKU convention, enforced** | `buildSku` exists and reuses each style's dominant token. It needs to be *in the create form*, proposing and validating rather than accepting free text. `create.ts:145` is still `req(p.colorwaySku)`. |
| **Barcode allocation in the UI** | The allocator and ledger exist and nothing in the interface calls them. A new variant should get a code on save, from the right range, recorded. |
| **Attribute completeness** | Colour, fibre, manufacturer and images are empty on 1,175 imported colorways. Loom's *wholesale* catalogue needs fibre and manufacturer; the registry does not. |
| **Customs fields** | HS code, customs description and weight are empty in the Threadflow feed. They must be fillable here or fixed at source, or Loom gets an incomplete customs payload. |
| **Bulk tolerance** | Paste a size run, fill a column, apply across selected rows. The editor already optimises for this; the builders should inherit it, not reinvent it. |

### 5.2 Livid product builder
Threadflow remains the origin for production styles. The builder covers what
Threadflow does not: imperfects, repairs, sale buckets, collabs — the rows that
today land on the improvised `7000000*` range.

### 5.3 External brand builder
Different rules and the model should say so: the barcode comes from *the brand's*
GS1 prefix, not Livid's; no Loom wholesale eligibility; `kind` and channel policy
set on create. Needs 2.6 decided.

### 5.4 Vintage builder
**Step 0 is access control** — this was the blocker when the vintage module was
paused, and it is unchanged: one shared password is not roles (Risk 2). Then the routing, which is already
decided: store vintage → Sitoo, online vintage → Shopify, both created in Origio.
One-of-ones (`VN-`, `EXT-VN-`) are excluded from duplicate detection by design.
