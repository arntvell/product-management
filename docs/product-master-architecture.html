Architecture proposal

Product Master

Turning product-management from a stateless Shopify editor into the single source of truth for all product data — Livid products pulled from Threadflow, plus manually-created external-brand products — that decides, per product, which channels it publishes to (Shopify → Sitoo, Loom B2B) and pushes that data outward.

Proposal — for review 2026-07-13 Companion to handoff.md No code yet
00

Summary

  1. Add a Postgres + Prisma persistence layer — the app has none today. This is the foundational change everything else depends on.
  2. Model products as Style → Colorway → Variant, with per-season data (prices, size availability, images, dropped/approved) and a global customs block + manufacturer + brand — mirroring Loom's model so the feed maps cleanly.
  3. Ingest from Threadflow (GET /products?seasonId=… + /manufacturers) on a daily schedule + manual trigger, with modes (full / prices-only / with-or-without images).
  4. Support manual creation of external-brand products (no Threadflow source).
  5. Track three independent lifecycle axes: per-channel publish state, per-season cancelled/dropped, archived. Missing-from-feed is never a delete.
  6. Publish per product to Shopify and/or Loom; reuse the existing Shopify mutations for the Shopify push, build the Loom feed per handoff.md.
  7. Coexist: the current live-Shopify screens keep running untouched; the master is built alongside under a new nav section.
  8. Accept the one write-back: per-variant weighted-average cost from Loom → store → forward to Shopify.
01

Guiding principles

  • The master owns the truth. Once a product lives here, the master decides what every channel sees. Channels are push targets, not editors.
  • Explicit lifecycle, never inference. A product vanishing from a Threadflow page does not delete it. Removal is an explicit archive/cancel signal — the rule Loom already enforces.
  • Stable internal IDs. The master mints its own immutable id per Style/Colorway/Variant and stores each source system's ids (Threadflow ids, Shopify GIDs, Loom keys). Matching is always on stable ids, never on renameable display strings.
  • Field ownership is explicit. Every field is owned by exactly one source at a time (Threadflow, Shopify-import, or authored-in-master). Syncs never clobber manager-authored data — see §5.3.
  • Idempotent, at-least-once sync. Re-running a sync or re-delivering a push is always safe.
  • Non-destructive coexistence. Nothing here changes or risks the existing Shopify editor until we deliberately migrate it.

Threadflow feeds Livid products in; external and carry-over goods enter by manual creation or a Shopify import. The master resolves everything into one model and pushes outward per-channel. Exactly one value flows back: weighted-average cost from Loom.

03

Coexistence strategy

We keep the current app fully functional and build the master next to it. No existing route, hook, or component is modified in the early phases.

The editor is core, not legacy

The rich editing today's app provides is not something we retire — it is the master's enrichment layer, reborn on a real data model. The only change underneath is the plumbing: instead of writing live to Shopify, every edit lands on the master record and the master pushes it outward. All of this stays first-class in the new Catalog, now editing master data:

  • Product properties — tags, status, vendor/brand, product type.
  • All ~17 custom.* metafields — descriptions, details, taglines, style name, color_hex, and the reference fields (same_product, style_with, care_page, fitguide, model_info, recommended collection, unisex style-with, men/women images).
  • Media — upload, gallery, drag-to-reorder, per-slot assignment.
  • Prices — variant price / compare-at, extended to season scope (§9).
  • Power tools — inline cell editing, find & replace, column picker, the care/fitguide/collection/model pickers, group auto-linking, and fit models.
  • Split by channel — descriptive fields can hold different values for Shopify (B2C) and Loom (B2B); the wholesale buyer reads different copy than the retail shopper (§4.3).

Carried into the master with the same UI components — what they write changes, not what they do.

04

Data model

Business vocabulary, aligned with Loom's so the feed maps cleanly:

ConceptMeaning
StyleThe garment (parent) — e.g. "Beth".
ColorwayOne colour of a style. This is the master "product" record.
VariantThe sellable size unit (SKU + barcode).
SeasonSelling season; prices, sizes, images, dropped flag are scoped to it.
BrandLivid or external.
ManufacturerFactory with address; used for Loom customs invoices.

}

  colorwayId  String

  @@unique([colorwayId, channel, field])
}

Notes on the model

  • The editor's fields all have a home. Everything editable today maps onto the master: product props (status, tags, vendor), the full custom.* metafield set (free-text + reference fields, edited via the same pickers), and the full media gallery (MediaAsset, upload + reorder). These are master-authored and pushed to Shopify via the existing mutations.
  • Reference metafields store target ids. sameProduct, styleWith, etc. hold GIDs / ids as today; Groups still populates sameProduct, Models still manages the fit-model metaobjects behind modelInfoId. Whether these Shopify page/collection/file references need master-native equivalents once Shopify is a pure push target is an open question (§11).
  • Customs placement. Threadflow returns customs at style level; Loom wants them at colorway level. We store the style-level value and expose a per-colorway override that falls back to the style.
  • Threadflow has no stable variant_id. Its variants carry only sku, barcode, dimensions, so the master mints the stable variant id and matches on variantSku within a colorway. Style/colorway do have TF ids.
  • CONTINUITY season models carry-over / external non-seasonal products, so everything still has season context (Loom needs it) without forcing a wrong real season.

4.3 · Channel-split content (B2B vs B2C)

The copy a B2B buyer reads in Loom is not the copy a B2C shopper reads in Shopify/Sitoo. So editable content is not one value fanned out identically — it is a base value plus per-channel overrides.

ClassFieldsBehaviour
Sharedidentity / SKUs, barcode, customs block, manufacturer, weight, country of originSingle-valued — same on every channel by definition.
Channel-splitdescriptions, details, tagline, style name, tags, product type, styleWith / recommendations, media selection & orderBase value + optional per-channel override (ChannelContent). Set exact list — §11.11.
Price-splitwholesale → Loom · MSRP/retail → ShopifyAlready handled by PriceType (§9), not ChannelContent.
Resolution & editor

The effective value for a (colorway, channel, field) is the ChannelContent override if present, otherwise the base column. A field with no override inherits the base — you only author a channel-specific version when it actually differs.

In the editor, a channel-splittable field shows a base plus a Shopify / Loom switch (or side-by-side columns) with an "inherit from base" default; overriding one channel never touches the other. Publish (§7) sends each channel its resolved value. Overrides are always MANUAL-owned (§5.3), so a Threadflow sync updates the base but never rewrites a channel override.

5.2 · Upsert rules

  • Match Style/Colorway on threadflowId, Variant on variantSku. Create-or-update; never delete on absence.
  • Barcode set-once: if incoming barcode is empty and we already have one, keep it (SS27 barcodes are blank until production).
  • Customs "don't clobber with empty": never overwrite a populated customs field with a blank value.
  • Prices: upsert (season, colorway, currency, type) rows from the prices object. Livid prices are Threadflow-owned (the calc lives there).
5.3 · Critical — field ownership / locking

Text will eventually be authored in the manager, but for now Threadflow text may be imported for SS27. To let both coexist without a sync wiping manual edits: each field has an owner. TF-sourced fields default to THREADFLOW; editing a field in the manager flips its owner to MANUAL (locked). A sync only writes fields it owns — manager-owned fields are skipped. A "revert to Threadflow" action re-hands ownership and re-pulls.

5.4 · Sync modes

Selectable per run and per schedule: full · no-images · prices-only · single-season · single-style. Each is recorded in SyncRun with counts and errors; one bad style never blocks the batch.

5.5 · Shopify carry-over import

Carry-over and external products already in Shopify need to reach Loom. A secondary importer reads existing Shopify products (reusing the current client) and creates Colorways with source = SHOPIFY_IMPORT into a CONTINUITY season. These then require the customs block filled before they can publish to Loom.

06

External product creation

  • Create Style → Colorway → Variant by hand for external brands (source = MANUAL).
  • A channel-target dialog on create/edit: choose Shopify and/or Loom (some products are B2B-only).
  • Input fields differ by destination. The form is grouped — master fields (brand, category, gender, customs, manufacturer) required for Loom; Shopify enrichment (descriptions, taglines, media) required for Shopify — and validates the required set per selected channel before publish is allowed.
  • Manufacturers can be created/edited here too, since external goods need the customs block for Loom.
07

Publishing

Per-colorway ChannelPublication rows drive everything. A product is pushed to a channel only when published = true for it. Each channel receives the resolved content — the ChannelContent override where one exists, otherwise the base (§4.3) — so Shopify gets the B2C copy and Loom gets the B2B copy from the same record.

7.1 · Shopify → Sitoo

Map master fields → Shopify product + custom.* metafields, reusing src/lib/shopify/mutations.ts (product update, metafields set, variant/price and media mutations). Store the resulting product GID in ChannelPublication.externalId. Sitoo is downstream of Shopify — no direct integration needed.

7.2 · Loom (B2B)

Build the Loom feed payload exactly per handoff.md: stable ids at every level, brand per product, the channels object, per-season cancelled/approved_for_production, prices as (currency × {msrp, ws}), the full customs block, manufacturer_id, and variants with barcode + dimensions using the 2-D SKU suffix rule (waist+length digits, no W/L).

  • Delivery is an open question (§11.1) — webhook push vs. Loom pull. Design the payload now; wire transport once agreed.
  • Change propagation via an outbox: any edit to a Loom-published colorway enqueues an event; a worker pushes to Loom keyed on stable ids, at-least-once, with a monotonic version so Loom drops stale/duplicate deliveries.
  • Images to Loom: likely re-host synced images in object storage and hand Loom fetchable URLs (§11.6).

08

Lifecycle — three axes

Treat these as three separate signals, not one status enum.

AxisStoredSet byEffect
Channel publish ChannelPublication.published Manager toggle, per product per channel loom:false (after true) → archive in Loom. Explicit, never inferred.
Cancelled / dropped SeasonEntry.cancelled Threadflow dropped, per season — changes each sync Hidden that season in Loom; existing orders struck-through; reversible.
Archived Colorway.archived Manager / channel-off Hidden across all seasons in Loom; history kept; reversible.

Hard delete is not exposed via the feed. Future-season products that never go to production and sit on no Loom orders can be deleted only via a deliberate admin action later — never via sync.

09

Pricing & cost write-back

  • Season-scoped prices as (season × colorway × currency × type) rows; MSRP in NOK, wholesale in NOK/EUR/USD; inherited by all variants (no per-size pricing). Precision Decimal(14,2).
  • Livid prices flow from Threadflow (the calc lives there) → master → channels. External prices are edited in the master.
  • Provide a calculation / margin view (in-price vs. out-price, gross margin) and keep season-level price history so buy/sell prices are visible over time.
  • Cost write-back — the only inbound write: an endpoint receives per-variant weighted-average cost (NOK) from Loom on each goods receipt, stores it on Variant.averageCostNok, and forwards it to Shopify (Sitoo picks it up natively). Contract shape is open (§11.7).
10

Sync mechanics & scheduling

  • Daily scheduled ingest + manual trigger per season/mode. On Vercel: a Cron route (/api/cron/threadflow-sync) protected by a secret; elsewhere a scheduled worker.
  • Idempotent, at-least-once; every entity carries a version / updated_at so re-delivery is safe.
  • Reconciliation: a periodic full snapshot per season as a safety net for missed pushes (cadence TBD, §11.8).
  • Observability: the SyncRun log surfaced in the UI — last run, counts, errors, retry.
11

Open questions

To resolve with the Loom and Threadflow owners. The numbering is referenced throughout this doc.

  1. Loom ingest contract — webhook push vs. pull; envelope, auth, batch size, event ids, versioning.
  2. Variant SKU ownership — master sends variant_sku (preferred) vs. Loom derives; confirm the 2-D suffix rule or plan a migration. Also confirm SKU is a safe match key given TF exposes no stable variant id.
  3. Manufacturer delivery to Loom — embedded in payload vs. separate endpoint.
  4. Season-less / continuity / external mapping — confirm the CONTINUITY season approach vs. a season-less mode.
  5. Weight unit — confirm Threadflow /products weight is kg (doc says yes; older feed was grams). Master stores kg.
  6. Image delivery to Loom — public URLs, signed URLs, or proxied bytes; per-season imagery.
  7. Cost write-back endpoint — confirm shape/auth for per-variant avg cost from Loom → master.
  8. Reconciliation cadence — frequency of full/delta snapshots.
  9. Hosting / deploy target — Resolved: Vercel → Vercel Postgres (Neon-backed) + Vercel Cron. Env in .env.local locally + Vercel Project Settings for deploy.
  10. Threadflow season identifiers — map TF seasonId/seasonCode to master Season records (a settings step).
  11. Channel-split field set — confirm exactly which fields are channel-splittable vs. shared (§4.3), and whether the split stays per-channel or later needs per-market / per-language granularity.
12

Phased roadmap

Each phase is independently shippable and leaves the existing Shopify editor untouched.

Phase 0

Foundations

Add Prisma + Vercel Postgres, schema.prisma, first migration, env wiring (DATABASE_URL; THREADFLOW_* / SHOPIFY_* already set). New Catalog nav shell and lib dirs. No behaviour change to existing screens.

Phase 1

Threadflow ingestion (read-only)

Typed TF client + manufacturer resolution; upsert engine with barcode set-once and don't-clobber-customs; manual sync trigger + season/mode selector; read-only browse. Goal: pull SS27 in and browse it.

Phase 2

Enrichment editor & external products

Carry the full editing suite onto the master — inline tags/status/vendor, all metafields, pickers, find & replace, column picker, group auto-link, fit models, and the media manager (upload + reorder) — with field ownership/locking. Plus manual external-product creation with per-channel validation and the Shopify carry-over importer.

Phase 3

Channel model + Shopify push

Publication UI (destinations per product); Shopify push mapping reusing existing mutations; store GIDs; publish / unpublish flow.

Phase 4

Loom push

Finalise the Loom ingest contract; build the feed payload; outbox + change-propagation worker; lifecycle signals; image re-hosting.

Phase 5

Pricing & cost write-back

Season-scoped price editing, margin view, price history; cost write-back endpoint → variant cost → forward to Shopify.

Phase 6

Scheduling & hardening

Daily cron, reconciliation snapshots, monitoring/alerting on sync failures.

Later · 7

Retire the live-Shopify plumbing

The editor's functionality already lives in the master (Phase 2). This phase only removes the old wiring — the pages that read/write Shopify directly — once the push flow is at parity. No editing capability is lost: it moved, it wasn't retired.
