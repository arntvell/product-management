# Loom → Origio: barcodes the warehouse scanned in

**For:** the Origio developer.
**Status:** built on Loom's side. Off until Livid enters your receiver URL and switches it on.

## 1. Why this exists

Pio matches goods to a purchase order by SKU, and the warehouse works by scanning. If
Origio has not barcoded a size yet, Loom does not send it to Pio. A delivery of that size
then blocks its inbound.

The workaround: an admin can send those sizes to Pio **without barcodes** so the purchase
order can go. Loom records every size sent this way. When the goods arrive, the warehouse
scans each size's barcode on Loom's **Ready to Ship → Missing barcodes** page. Each scan:

1. becomes the size's barcode in Loom,
2. is pushed to Pio straight away, then read back to confirm Pio took it,
3. once every size on that inbound has a barcode, is sent to **you** in one event.

Origio is the product master, so the barcode has to end up in Origio, and Origio pushes it
on to Shopify, Sitoo and its other channels. Loom has no way to write to Origio, so we
tell you instead.

**What we need from Origio:** for each row, file `barcode` on the size, then push it to
your channels as you would for any barcode change. When your feed next sends that size
with the same barcode, the loop is closed.

## 2. The event: `barcodes.ready`

**When we send it:**

- **One event per inbound**, sent once **every** size Loom sent to Pio without a barcode for
  that inbound has one. You get the whole delivery in one go, not a trickle.
- **Corrections.** The warehouse can correct a barcode until the inbound closes. A
  correction made after the event went out produces a **new event** for the same batch. It
  has a higher `revision` and `is_correction: true`, and carries the whole batch again.
  **Process the highest revision you have seen for a `batch_id`, and ignore lower ones.**
  Events can arrive out of order after a retry.

### Transport

This is the same transport Loom uses with every partner.

| | |
|---|---|
| Direction | Loom → Origio |
| Method | `POST` |
| Endpoint | **Yours**, any path. Livid enters it in Loom under Settings → Integrations → Origio. |
| Content type | `application/json` |
| Auth | HMAC-SHA256 over the raw request body, in header **`X-Loom-Signature: sha256=<hex>`** |
| Secret | Generated by **Loom** (prefix `loom_whsec_…`) and shown once to Livid, who passes it to you. |
| Timeout | **15 s.** Answer quickly and do your own work afterwards. |
| Retries | `1m, 5m, 15m, 30m, 1h, 2h, 6h`: 8 attempts over about ten hours. After that we stop and flag it for a human. |

Headers on every delivery:

```
X-Loom-Event:      barcodes.ready
X-Loom-Event-Id:   loom_evt_…      ← STABLE across retries. This is the dedupe key.
X-Loom-Delivery:   loom_dlv_…      ← changes on every attempt. Never dedupe on this.
X-Loom-Timestamp:  1789041242      ← unix SECONDS
X-Loom-Signature:  sha256=<hex>
User-Agent:        Loom-Webhooks/1.0
```

**How we read your answer:**

| You answer | We do |
|---|---|
| any `2xx` | Done. This event is never sent again. |
| `401`, `408`, `429`, any `5xx`, or a timeout | Retry on the ladder above. |
| any other `4xx` | Stop. We treat it as a permanent refusal. Livid can press "Notify Origio again" once you have fixed it. |

If you have already processed an event id, answer `2xx` again. A retry after a lost
response is normal.

### Verifying

Compute HMAC-SHA256 over the **raw request body bytes**, hex-encode it, and compare it to
the header with the `sha256=` prefix stripped. Compare in constant time.

```js
const provided = (req.get('X-Loom-Signature') ?? '').replace(/^sha256=/i, '');
const expected = crypto.createHmac('sha256', LOOM_WEBHOOK_SECRET)
                       .update(rawBody)          // the RAW bytes, not the parsed object
                       .digest('hex');
if (provided.length !== expected.length ||
    !crypto.timingSafeEqual(Buffer.from(provided), Buffer.from(expected))) {
  return res.status(401).json({ error: 'invalid signature' });
}
```

### Body

```json
{
  "event": "barcodes.ready",
  "event_id": "loom_evt_3f0c…",
  "created_at": "2026-10-25T10:00:05.000Z",
  "data": {
    "batch_id": "cm…",
    "inbound_ref": "142",
    "po_number": "PO-2026-0311",
    "supplier": "Atelier Nord",
    "revision": 6,
    "is_correction": false,
    "barcodes": [
      {
        "sku": "TIA-JPR-32-32",
        "product_sku": "TIA-JPR",
        "origio_variant_id": "V-9002",
        "size_label": "32/32",
        "barcode": "7071234500025",
        "previous_barcode": null,
        "entered_at": "2026-10-25T09:58:41.000Z"
      }
    ]
  }
}
```

| Field | Notes |
|---|---|
| `batch_id` | Loom's id for this inbound's set of sizes. Stable across revisions. |
| `inbound_ref` / `po_number` / `supplier` | For your logs and for humans. Do not key on them. |
| `revision` | Increases with every barcode saved on the batch. It can jump by more than 1. |
| `is_correction` | `true` when an earlier revision of this batch was already sent to you. |
| `barcodes[].sku` | The variant SKU, as Loom and Pio hold it. |
| `barcodes[].origio_variant_id` | Your own `variant_id` from the feed, when you sent one. **Prefer it for matching.** It is `null` for sizes created before you sent stable ids. |
| `barcodes[].barcode` | Digits only. EAN-8, UPC-A, EAN-13 or GTIN-14, check digit verified. Loom refuses a barcode that another live size already has. |
| `barcodes[].previous_barcode` | Set when this revision changes the barcode the previous event gave for the size. File the new one in its place. |
| `barcodes[].entered_at` | When the warehouse saved it. |

The event only lists barcodes **the warehouse entered**. A size you barcoded yourself before
the warehouse got to it is left out, because you already have it.

## 3. The pull: `GET /api/origio/v1/warehouse-barcodes`

This is a backstop for the webhook, and useful for reconciling. It uses the same Bearer
token as your other `/api/origio/v1` reads and needs scope `origio:read`.

```
GET /api/origio/v1/warehouse-barcodes?since=2026-10-25T09:00:00.000Z&limit=200
```

It returns every barcode the warehouse entered after `since` (exclusive), oldest first. To
page, pass `nextSince` back as `since` until it is `null`. A correction moves the size's
`entered_at` forward, so the size shows up again.

```json
{
  "ok": true,
  "generatedAt": "…",
  "rowCount": 1,
  "nextSince": null,
  "rows": [
    {
      "batch_id": "cm…",
      "inbound_ref": "142",
      "po_number": "PO-2026-0311",
      "sku": "TIA-JPR-32-32",
      "product_sku": "TIA-JPR",
      "origio_variant_id": "V-9002",
      "size_label": "32/32",
      "barcode": "7071234500025",
      "entered_at": "2026-10-25T09:58:41.000Z",
      "loom_barcode": "7071234500025",
      "in_pio": true
    }
  ]
}
```

- `loom_barcode` is the size's barcode in Loom **now**. If it differs from `barcode`, your
  feed has already sent a different one, and yours won.
- `in_pio` is `true` once Pio has confirmed the barcode on read-back.

## 4. If Origio disagrees

Origio stays the master. If your feed sends a **different** non-empty barcode for one of
these sizes, Loom replaces its own (audited) and pushes yours to Pio. The warehouse page
then shows the size as "Origio has filed … for this size". An **empty** barcode in your
feed never clears one the warehouse entered.

## 5. Testing checklist for your side

- [ ] Signature verifies against the raw body; a tampered body gets `401`.
- [ ] A repeated `X-Loom-Event-Id` answers `2xx` and changes nothing.
- [ ] A lower `revision` arriving after a higher one for the same `batch_id` is ignored.
- [ ] A `previous_barcode` row replaces the old barcode instead of adding a second one.
- [ ] Each filed barcode reaches Shopify and Sitoo through your normal channel push.
- [ ] Your next feed sends the same barcode for these sizes.
